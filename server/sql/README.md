# db_euniverse: E-Universe's SQL Server database

E-Universe keeps two stores:

| Store | Keeps |
|---|---|
| **MongoDB** (Atlas) | User accounts and sessions, the ERMS records, and their history |
| **SQL Server** `db_euniverse` (office server) | Everything else, moved phase by phase |

The legacy desktop ERMS databases on the same server (`dbmain_records`,
`dbmain_ermssublegal`, `dbmain_ermssublaboratory`) are read-only to E-Universe
(`services/legacySql.js`) and are never written to.

## Security

- **Login `eu_app`** owns `db_euniverse` and `db_euniverse_test` and has no
  rights anywhere else. The setup script checks this by signing in as `eu_app`.
- **Its password** is 40 random characters, generated by `npm run sql:setup`
  and stored encrypted with `CONFIG_ENCRYPTION_KEY` in `app-config/euniverse-sql`.
  It is never printed. Rotate it with `npm run sql:setup -- --rotate-password`.
- **Every value** goes in as a parameter. Table and column names come from the
  code, never from a request.
- **Reachable** only on the office network and, for `tag:ucds-server` machines,
  through the office server's Tailscale route (`10.14.77.248:1433`). Port 1433
  is never exposed to the internet.

## Commands (in `server/`)

| Command | Does |
|---|---|
| `npm run sql:setup` | Creates the databases and `eu_app` if missing, then applies migrations. Safe to run again |
| `npm run sql:migrate` | Applies pending migrations to `db_euniverse` (`-- --test` for the test database). Run on every deploy |
| `npm run sql:status` | Shows the schema version and anything pending, without changing anything |

## Migrations

`sql/migrations/NNN_name.sql`, applied in order, each in a transaction, and
recorded with its checksum in `dbo.schema_migrations`. **Never edit an applied
migration**: add a new one. A changed file is refused. Separate batches with a
line containing only `GO`. E-Universe's tables live in the `eu` schema.

## Not a bottleneck

- One connection pool per process (`services/euSql.js`), reused by every request.
- Rows that need not hold up a request (audit trail, history, events) go
  through `createBatchWriter`. Requests return at once; rows are inserted in
  bulk every two seconds or every 200 rows. If SQL Server is briefly
  unreachable they wait and go in later.
- Every table a screen pages through gets an index on the columns it filters
  and sorts by, in the migration that creates it.
- For the live site the database is on the same machine as E-Universe, so it
  is closer than Atlas.

Stays in MongoDB by design: accounts and sessions, `erms-records`, `erms-documents`,
and the record histories the ERMS tracking screens read
(`legacy-erms-records-filelogs`, `legacy-erms-records-file-history`).

### Switching a history (`npm run sql:move`)

```
npm run sql:move -- status                     mode and counts, nothing changed
npm run sql:move -- all --mode=dual            copy what is missing; write both, read MongoDB
npm run sql:move -- all --mode=sql             copy again, refuse unless counts match, then SQL only
npm run sql:move -- sign-in-history --mode=mongo   roll back one history
```

The copy is safe to repeat (rows keep their MongoDB `_id`). Switch to `sql`
only when every running server has this code: an older server keeps writing
to MongoDB alone, and the copy just before switching picks those rows up.
MongoDB's copies are not deleted by any of this.

Each phase copies the data (recorded in `eu.data_moves`), switches reads and
writes behind a setting, verifies counts, and keeps the MongoDB copy for a
period before removing it. Rolling back means switching the setting back.

## Backups

`db_euniverse` uses the SIMPLE recovery model, so its transaction log cannot
grow without bound. **Add it to the office server's nightly SQL Server backup**
(a full backup of `db_euniverse` each night).
